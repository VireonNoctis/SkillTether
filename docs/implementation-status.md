# Implementation status

This page describes the repository implementation, not the entire long-term SkillTether vision. For traceability by requirement and test evidence, see [the readiness audit](readiness-audit.md). For CLI examples, see [the usage guide](usage.md).

## Implemented and regression-tested

### Package inspection and structural validation

- Read-only package inventory with SHA-256 fingerprints that include file mode/permission metadata.
- Bounded traversal, directory depth/count limits, per-file and aggregate byte budgets, non-following regular-file reads, and rejection of package-root symlink aliases, in-package symlinks, and special filesystem entries. The opened file descriptor is checked against the identity observed during enumeration; a replaced entry is reported as `FILE_IDENTITY_CHANGED` and makes comparison structurally fail. Directory-enumeration errors fail closed instead of allowing `os.walk` to silently omit an unreadable subtree. Tests cover a regular file passed as a root, an in-package symlink directory that must not be traversed, and the file-count limit.
- Source packages are inspected but never intentionally rewritten. Candidate and approval output are staged separately, staged content and metadata are rechecked, and failed translation/approval does not publish a partial package.
- UTF-8 validation for expected text/script resources; arbitrary binary assets remain byte-oriented rather than being misclassified as malformed text.
- YAML frontmatter and required `SKILL.md` metadata checks, including required non-empty `name` and `description`, Unicode lowercase alphanumeric skill-name syntax (1–64 characters, single hyphen separators), trimmed NFKC comparison with the package directory without rewriting identifiers; tests include compatibility-form full-width Unicode names, description length, and types for supported optional fields. Present `compatibility` values must be non-empty strings of at most 500 characters; explicit `null` is invalid. Non-string top-level YAML keys receive a dedicated high-severity finding rather than crashing unknown-field handling. A leading UTF-8 BOM and CRLF-delimited frontmatter are accepted without rewriting original file bytes. Translation and MDX detection keep frontmatter opaque, invariant suggestions skip the complete header, and malformed frontmatter is refused for manifest drafting.
- Optional `license`, `compatibility`, `metadata`, and experimental `allowed-tools` are validated when present but are not required. Unknown frontmatter fields receive a low-severity notice rather than an automatic blocking failure. The bundled `extension-skill` fixture verifies this policy: SkillTether accepts with a low warning while pinned `skills-ref@v0.0.1` rejects the unknown field; this difference is intentional and documented. Metadata keys and values must be YAML strings; a numeric-key/value fixture verifies SkillTether rejects scalar coercion that the pinned reference accepts.
- Local Markdown links and images, GFM table and footnote content, percent-decoded fragments, malformed local-link URL findings, conventional resource references, duplicate Unicode heading anchors, and referenced package resources are checked within bounded reads. File URIs and Windows drive-absolute, drive-relative, rooted, or UNC link targets produce review-required findings instead of being treated as ordinary external schemes. Duplicate heading suffix allocation avoids collisions with literal headings that already use a generated suffix. External URLs are not fetched. Invalid decoded filesystem targets (including percent-encoded NUL characters) produce a dedicated finding instead of aborting inspection.
- Common portability hazards are detected deterministically: Windows-reserved component characters/names and trailing periods/spaces, plus case-folded Unicode NFC path collisions. The check is conservative and does not emulate every host filesystem.
- Static syntax parsing is applied to supported Python, JSON, YAML, TOML, and XML resources. When trusted local tools are installed, Bash/sh (`-n`), Node.js JavaScript (`--check`), and PowerShell (`Parser.ParseInput`) are used in parse-only mode with source supplied on stdin, a minimal environment, a three-second per-process timeout, and a maximum of 16 checks per package. Missing parsers, timeouts, syntax errors, and exhausted-check budgets are explicit findings. No package script is executed and no parser is downloaded. TypeScript, batch-file, and runtime-semantic analysis are not implemented.
- Protected-token policies support configured literals and regular expressions, bounded token/pattern inputs, overlap handling, and conservative screening for common risky regex shapes. This screening does not prove all patterns computationally safe.

### Protected content, translation, and comparison

- Protected spans cover common machine-facing material such as code fences, inline code, URLs, command flags, environment variables, paths, and configured identifiers/literals.
- Translation is provider-neutral through the `TranslationAdapter` interface. The default identity adapter makes no network request and leaves prose unchanged; it is a pipeline test, not a translator. The generic JSON HTTP adapter requires an endpoint and explicit `--allow-remote` consent. A CLI regression verifies the consent gate returns before any provider request or candidate/report/history publication.
- Translation performs a local whole-package preflight before the first provider call. The workload is capped at 10,000 translation requests and 10 MiB of aggregate outbound request bodies. The HTTP adapter also enforces request-count/byte budgets, a 2 MiB per-line request/response cap, a 10 MiB aggregate response cap, positive timeouts no longer than five minutes, and endpoint URL restrictions. Production endpoints must use HTTPS; plain HTTP is limited to loopback.
- Markdown translation uses one shared parser profile: CommonMark plus GFM-like tables, strikethrough, task lists and alerts, plus footnotes and definition lists. Parser inline source maps gate translation eligibility so only lines owned by inline prose nodes are sent to adapters; frontmatter, fenced/indented code, and non-inline block content remain opaque. Nested list/blockquote prefixes are retained. The transformer masks/restores supported syntax and opaque regions: frontmatter, fenced/indented code, inline-code spans, URLs and link/image/reference-link/footnote delimiters, emphasis delimiters, task-list checkboxes, escaped punctuation, hard line breaks, HTML tags, and table pipes. Table-cell prose can be translated while separators stay intact. Multiline HTML comments and recognized code-bearing HTML blocks remain opaque. The parser requires markdown-it-py 4.1+, mdit-py-plugins, and linkify-it-py.
- Translation fails closed on deleted/duplicated/reordered syntax placeholders, provider-injected line breaks or unsupported controls, invalid response values, exceeded budgets, or a changed parser-visible Markdown structure signature. Obvious MDX imports/exports, JSX tags, and JavaScript expressions outside code examples produce a high-severity unsupported-syntax finding; MDX is never evaluated. This is not a full CommonMark/MDX AST transformation.
- Package comparison covers line-block/content differences, protected tokens and their order, file paths, non-text resource hashes/modes, and human-authored invariants. Added/omitted-content findings are alignment evidence, not a complete classification of new operational instructions.
- Invariant source paths, line ranges, and quoted source excerpts are checked against the current source. Draft cue profiles cover English, French, Spanish, German, Portuguese, Italian, Arabic, Hindi, and Russian. The curated 45-positive fixture asserts TP=45, FP=0, FN=0 and computes exact-match precision/recall separately for each of the nine languages and four rule families; this is a regression result on a small authored corpus, not a representative accuracy estimate. Unknown languages receive no automatic suggestions. The CLI writes an empty, unreviewed manifest with an explicit message when a syntactically valid locale has no built-in cue profile. Candidate and target-language marker lists remain unreviewed heuristics. A separate realistic-document fixture covers regional tags en-GB, fr-CA, es-MX, de-AT, pt-BR, and it-CH with 24 authored positives and explicit descriptive/code negatives; its metrics are reported separately and do not establish dialect-level production accuracy. Reference-comparison fixtures cover a Unicode skill name, the 64-character name/1,024-character description/500-character compatibility maximums, and invalid name/compatibility boundaries.
- When stopword-filtered, Unicode-normalized word overlap cannot locate a target excerpt, comparison can use preserved line position only when source/target line counts match and the manifest has a source line. The report marks this as a high-uncertainty heuristic; it is not a semantic match and does not remove critical human sign-off.
- Invariant manifests optionally accept paired `target_lines` and `target_text` anchors for the exact localized passage in the corresponding relative resource. The comparator verifies the current target excerpt deterministically and uses it instead of word-overlap/positional guessing; stale anchors produce a deterministic critical finding and are permanent approval blockers. A valid anchor improves evidence location only—it does not prove semantic equivalence or remove critical human sign-off. Expected numeric literals normalize Unicode decimal digits (category `Nd`) before exact boundary matching; separators, units, and number words are not converted or inferred. Cross-script target anchors improve location evidence only and retain critical human sign-off.
- Invariant source paths, line ranges, and quoted source excerpts are checked against the current source. Stale or invalid anchors create deterministic critical findings and cannot be bypassed by an approval disposition; fix the manifest and rerun comparison.
- Count-preserving reordering of protected machine-facing tokens can be flagged as a high-uncertainty heuristic finding.

### Invariants, reports, approval, and local history

- `init-manifest` creates an unreviewed YAML draft. Heuristic suggestions skip fenced/indented code examples, recognized HTML `<pre>`/`<code>` examples, headings, table rows, descriptive numeric facts without operational cues, and candidate lines over 1,200 characters. Candidates can still be missed or misclassified and require human curation.
- Invariant manifests and comparison reports use versioned Pydantic contracts and JSON Schemas. Locale fields share dependency-free BCP 47 structural validation, including subtag ordering, extlang structure, variant uniqueness, extension singleton uniqueness, and private-use forms. IANA registry membership checks and canonicalization are not implemented.
- Findings record evidence/locations where available, a rule identifier, detection method, explicit uncertainty, severity rationale, review disposition, reviewer details, and timestamped review history. Approval report inputs retain their lexical path until the bounded no-follow reader opens them, so a symlink alias is not silently canonicalized and followed.
- Review decisions append to history; changing a decision does not silently erase prior dispositions. Approval/export requires structural success, matching source/target/manifest/policy fingerprints, a reviewed invariant manifest, and approved decisions for critical or review-required findings. Before publication, the CLI regenerates the comparison and requires all immutable machine-produced report evidence to match; reviewer disposition/history fields are the only mutable evidence fields. Invalid frontmatter keys/optional-field types, invalid UTF-8 text resources, and unsafe decoded local-link paths now set structural failure and cannot be waived by approval.
- JSON/Markdown reports are written atomically, use restricted POSIX permissions where supported, and are guarded against unsafe package-overlapping output paths. Markdown reports fence untrusted contexts and notes.
- Common credential-shaped values are redacted or rejected in selected report/review fields. This is a limited guardrail, not a complete secret scanner.
- Optional HMAC-SHA256 sealing can verify report integrity before review/export. It is symmetric integrity protection, not reviewer authentication or non-repudiation.
- Optional SQLite history keeps run metadata, locale/provider/status values, and package fingerprints, not source/target document text or credentials. Local history improves traceability but is not itself cryptographically tamper-evident.
- The offline reviewer workbench in reviewer/index.html loads a user-selected JSON report, filters findings, displays untrusted evidence as plain text, and appends timestamped decisions to unsigned reports before exporting a new JSON file. It makes no network requests and uses no browser storage. Signed reports are read-only; the CLI remains authoritative for signature verification and approval.

## Explicit limitations and non-claims

- No automated guarantee of translation fluency, semantic equivalence, completeness, or safety. Human review is required for critical or ambiguous meaning.
- Invariant candidate generation and token/order/context heuristics are incomplete, language-dependent, and not a calibrated semantic classifier.
- Markdown safeguards cover a documented GFM-like/Pandoc subset through a shared parser, AST-based inline-line eligibility, and lexical masking; they are not a complete source-preserving CommonMark/MDX AST transformation. MDX-specific syntax is flagged and direct translation fails closed; MDX is not interpreted. Unusual extensions and complex nested constructs require review.
- External URL reachability, IANA registry validation/canonicalization, TypeScript/batch parsing, and full shell/JavaScript/PowerShell semantic analysis are unsupported. Local Bash/sh, JavaScript, and PowerShell syntax checks are parse-only, optional by parser availability, and bounded to 16 files per package.
- No automatic protected-token rename mapping; changed identifiers must be reviewed rather than silently renamed.
- No bundled vendor SDK, hosted translation service, API-key management service, or built-in credentials. Provider privacy/retention remains the user's responsibility after explicit consent.
- No comprehensive secret scanner, cryptographic reviewer identity, or tamper-proof local history.
- The browser workbench is intentionally plain HTML/JavaScript, not a production Svelte application. It edits reports only in memory and does not verify HMAC signatures, authenticate reviewer identity, or replace CLI approval.

## Specification boundary

The normative format reference is the [official Agent Skills specification](https://agentskills.io/specification). SkillTether keeps base-format validation separate from additional package-integrity and localization safeguards. See [spec-compatibility.md](spec-compatibility.md) for the boundary and the limitations of the pinned reference validator.
